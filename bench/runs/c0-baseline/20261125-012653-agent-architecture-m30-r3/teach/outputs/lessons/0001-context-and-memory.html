Context and memory: what your assistant can see and remember

By the end of this lesson you can write a memory plan for your makerspace assistant: what the model sees at each step, what gets saved between visits, how it finds a manual page, and roughly how many tokens a request costs.

Objective O3: context and memory in an agent About 30 minutes Builds on the language model and the agent loop
Why this matters for you

Your assistant has to answer from long machine manuals, handle each student's training status across visits, and stay inside a small budget. All three come down to one design question: what text do you put in front of the model, and when? That is a strong thing to be able to defend at your design review.

Warm-up 2 min

Answer from memory before you open each answer. The effort of recalling is what makes it stick.

Recall 1

When a language model writes an answer, what are the two places its information can come from?

Check your answer

From patterns learned in training, and from the text it is given as input. Nothing else. Today is all about that second source, because it is the one you control.

Recall 2

Describe the agent loop in your own words. Include who carries out each action.

Check your answer

The model gets a goal and a set of tools. It asks for an action. Your program carries that action out and gives the result back to the model. This repeats until the model writes a final answer or a limit is reached. The model only asks; it never runs a tool itself.

The context window: the model's desk 4 min

Picture a student helper at the makerspace front desk. This helper can only use what they learned before the job, plus whatever papers are on the desk right now. The manual in the cabinet does not help until someone puts a page on the desk. And the desk has a fixed size.

A language model works much like that. The desk is the context window: all the text the model can refer to while it generates a response, including the response itself. The documentation for one model provider calls it working memory, separate from what the model learned in training.

Measured in tokens

The window's size is counted in tokens, the units a model uses to process text. A token can be a whole word, part of a word, a single character or a punctuation mark. For English, a common estimate is about 4 characters per token, so 100 tokens is roughly 75 words (token guide). Each model family splits text its own way, so treat this as a planning estimate.

For example, a 300-word manual page is about 400 tokens. Windows are large: the documentation above lists sizes of 200,000 and 1 million tokens for its models. Large is still not unlimited, and you pay for what you put in.

What takes up room

Here is what your program might send for one student question. Two terms are new. The system prompt is your standing instructions to the model, such as "You help students at the makerspace." A tool definition is the written description of one tool: its name, what it does and the inputs it takes.

The rule is simple: everything in the request counts, including the system prompt, every message, tool results and tool definitions. The model's output counts as well (context window docs). If the input alone is bigger than the window, that provider's service rejects the request with an error.

Check yourself

Your program sends the definition of book_slot with a request, but the model never asks for that tool. Does the definition use context space?

Show the answer

Yes. A definition is part of the request, so it fills space and costs tokens on every call that includes it.

Between steps: your program keeps the list 5 min

A student asks: "What bed temperature should I use for PETG, and is the 3D printer free Friday?" (PETG is a common printing plastic.) The assistant needs a manual search, then a calendar check, then an answer. That is three model calls. A step here means one model call, plus running the tool it asks for, if any.

What does the model remember from the first call when the second one starts? On its own, nothing. The service is stateless: it keeps no record of the conversation for you, so each request must carry the full history. One provider's guide to its Messages API says exactly this. (An API is the interface your code uses to call a service.)

Some services offer to store the history on their side. That changes who holds the list. The model still works only from what is placed in its context.

So who remembers that the manual search already happened? Your program does. It holds a Python list, adds each new item to it, and sends the whole list again. In this sketch, call_model, run_tool and tool_result are placeholder functions, not a real library.

messages = [{"role": "user", "content": question}]

for step in range(10):                        # step limit
    reply = call_model(system, tools, messages)
    messages.append(reply.message)            # keep the request
    if reply.tool_request is None:
        break                                 # final answer
    result = run_tool(reply.tool_request)     # program runs it
    messages.append(tool_result(result))      # keep the result

Read the two append lines again. They are the assistant's whole memory between steps. If you drop the second one, the model never learns what the search found. It may ask for the same search again, or guess.

Why the cost grows faster than you expect

Providers charge by the token, and input, cached input and output can each have a different price (token guide). Because the history is sent again on each call, you pay for early items more than once.

Worked example: count the input tokens

Made-up but reasonable sizes: system prompt 600, tool definitions 900, question 30. Each tool request is 50. The manual search returns 1,200 and the calendar returns 200.

  1. Call 1 sends the fixed parts and the question: 600 + 900 + 30 = 1,530. The model asks for the manual search.
  2. Call 2 sends all of that, plus the request and the result: 1,530 + 50 + 1,200 = 2,780. The model asks for the calendar.
  3. Call 3 adds the next request and result: 2,780 + 50 + 200 = 3,030. The model writes its answer.
  4. Total input is the sum of all three calls: 1,530 + 2,780 + 3,030 = 7,340 tokens.

The biggest single context was 3,030 tokens, but you paid for 7,340. Window size is about the largest call. Cost is about the sum of the calls.

The same holds across turns of one chat. If the student then says "book it," the next request still carries the earlier question, tool results and answer. That is how the model can work out what "it" means. Each turn's input holds the previous history plus the new message (context window docs).

Check yourself

The student types "book it" in the same conversation. What should your program send so the model can tell what "it" is?

Show the answer

The earlier messages plus the new question (along with the usual system prompt and tool definitions). The history is the only record of what "it" means.

When the context gets crowded 4 min

Imagine a student who chats for an hour while fixing a failed print. Twenty manual excerpts pile up in the history. Somewhere near the start they said, "I'm using the small printer, not the big one."

Two problems appear. Cost rises on every call, as you just saw. And the model may get worse at using what is there. This is called context rot: as the number of tokens grows, the model's accuracy and recall tend to degrade (context window docs).

Position can matter too. A 2023 study, Lost in the Middle, found that the models it tested often did best when the relevant text was at the start or end of a long input, and significantly worse when it was in the middle. Newer models may differ in degree, so test yours rather than assume.

A common mix-up

"A bigger context window solves memory. Just send everything." It is tempting because it needs no extra code. But a bigger window only raises the limit. You still pay for each token on each call, and extra text can make the important part harder to use. The goal is the smallest set of useful tokens that gets the job done (context engineering guide).

Choosing what goes into the context, and keeping it tidy as the agent runs, is called context engineering (same guide). Here are two tools for a long conversation, from lighter to heavier.

1. Clear old tool results

A manual excerpt from twenty turns ago has usually done its job. Your program can replace it with a short stub such as "[manual search result removed: printer manual p. 14]". The model still sees that a search happened, and can search again if needed. The guide calls this one of the safest, lightest forms of the next technique.

2. Compaction

Compaction means summarizing a conversation that is nearing the window limit, then continuing with the summary in place of the full history. For the hour-long chat, the summary might read: "Small printer. PETG. First layer not sticking. Bed already cleaned. Next idea: raise bed temperature."

A summary is shorter because it leaves things out. The guide warns that overly aggressive compaction can lose subtle but important context. So tell the summarizer what must survive: the machine, what was tried, any safety warnings and the open question.

Check yourself

Old manual search results from twenty turns ago are filling most of the context. What is the lightest sensible fix?

Show the answer

Clear the old results. They are large, already used and can be fetched again.

Between sessions: only what you save 5 min

On Monday a student says, "I'm color-blind, so please don't describe indicator lights only by color." They close the app. On Thursday they come back. A session is one such visit, with its own conversation. Thursday's message list starts empty.

A common mix-up

"The assistant will just remember. It learned that on Monday." It is tempting because some chat products seem to remember you, and a person at a desk would. But using a model does not, by itself, give your assistant a record of Monday. For Thursday's model call to know the fact, your system must save it somewhere outside the context and then put it back in. The same goes for which tools it picked last time: no record in context, no memory of it.

That gives you two kinds of memory (LangChain memory overview):

  • Short-term memory keeps track of one conversation, such as the message list in your loop. A program can also save it to disk, so a chat survives a restart.
  • Long-term memory keeps information across conversations and sessions, in a store your program can read later, such as a database.

Notes as memory

The simplest long-term memory is a note. In structured note-taking, the agent regularly writes notes that are kept outside the context window, then reads them back when useful. A to-do list or a plain notes file both count (context engineering guide).

Notice who does what, as with any tool. The model can ask to save a note through a tool such as save_note(text). Your program writes it to storage. On a later visit, your program loads it into the context, or offers a tool that reads it.

What deserves saving?

The same overview sorts memories into three types. Here they are with makerspace examples.

TypeHoldsMakerspace example
SemanticFacts"Needs light colors described another way."
EpisodicPast events"Monday: PETG print failed on the first layer."
ProceduralRules for doing tasks"Confirm the time before booking." (often kept in the system prompt)

Here is my design advice for your project. If another system already holds the official answer, look it up there instead of keeping a copy in notes. Training status is the key case. It does need to persist between visits, but it belongs in the makerspace's training record, read with check_training_record. A note based on "I did the training" could be wrong, and it could unlock a dangerous machine.

Also file every note under one student's ID, and load only that student's notes. Otherwise one person's details can show up in another person's chat.

When to write a note

You can save during the conversation, so the note is available at once, though this adds delay and gives the model a second job. Or a separate job can save afterwards, which avoids the delay but leaves the memory out of date until it runs (memory overview). For a first version, saving a few clear preferences during the chat is easy to test.

Notes also need upkeep. If a preference changes, update or delete the old note, or the model may be handed two facts that disagree.

Check yourself

Which item is the best candidate for a student's long-term notes?

Show the answer

The preference for short, numbered instructions. It stays true, helps later and has no other home.

Retrieval: finding the right page 5 min

Suppose you have six machine manuals of 40 pages each. At about 400 tokens per page, that is 240 × 400 = 96,000 tokens. A student asks one question whose answer is on one page.

Retrieval means searching a collection and putting only the relevant pieces into the context. It is how a large body of text can act as memory: stored outside, brought in when needed.

First, should you retrieve at all?

Compare sending all the manuals with every call against the worked example's search. Without a search step, the same question takes two calls: 97,530 tokens, then 97,780 with the calendar request and result. That totals 195,310 input tokens, against 7,340 with retrieval: about 27 times as many.

Sending everything can still be reasonable. A 2024 article on retrieval suggests that a knowledge base under about 200,000 tokens (roughly 500 pages) can simply go in the prompt, helped by prompt caching. Caching lets a provider reuse a repeated chunk of input at a lower price. It changes what you pay for those tokens, but they still fill the window (context window docs).

So "it fits" does not settle it. With a small budget, estimate the cost both ways using your provider's real prices, and test which one answers better.

How basic retrieval works

You cut each manual into chunks, passages usually no longer than a few hundred tokens. You prepare them once for searching. Then, for each question, you search, take the best few chunks and add them to the context (retrieval article). In your agent, that search can be the search_manuals tool.

Two ways to search

Keyword search finds chunks that share words with the query. Here is a toy version in Python.

chunks = [
  {"page": "laser p.12",
   "text": "reducing charring raise speed or lower power"},
  {"page": "laser p.3",
   "text": "start the exhaust fan before every cut"},
]

def search(query, k=1):
    words = set(query.lower().split())
    def score(chunk):
        return len(words & set(chunk["text"].split()))
    best = sorted(chunks, key=score, reverse=True)[:k]
    return [c for c in best if score(c) > 0]

Trace it. For "how to stop charring", page 12 shares one word, "charring", and page 3 shares none. Page 12 wins. For "my edges look burnt", no words match, so the function returns an empty list. The right page was there, under different words.

Real keyword rankers, such as one called BM25, are far better than this word count. They are especially good with exact identifiers and technical terms, such as part numbers (retrieval article).

Embedding search compares meaning. An embedding is a list of numbers that a special model produces for a piece of text, so that texts with related meanings get similar numbers. You embed each chunk once, embed the query, and pick the closest chunks. This can connect different wording, but it can miss exact matches. Many systems combine both methods (same article).

Two traps

Chunks lose their surroundings. A chunk saying "Set it to 80 degrees" does not say which machine or what "it" is. Add a short label to each chunk before indexing, such as the machine, section and page. The article reports fewer failed searches when each chunk gets explanatory context.

How many chunks? Too few may miss the answer; more cost more tokens. In that article's tests, 20 chunks beat 10 or 5. Your manuals may differ, so write a list of real student questions and check whether the right page comes back.

Fetching just in time

An agent can also look things up step by step. It keeps light references, such as file names or page titles, and loads the full text only when needed. This is just-in-time retrieval. It keeps the context lean but takes longer. A mix often works: load a little up front and fetch the rest on demand (context engineering guide). For example, put the list of manuals in the system prompt and let the model search inside them.

Check yourself

A student writes, "My cut edges look burnt." The manual's section is titled "Reducing charring." Which search is better placed to connect them?

Embedding search. The wording differs but the meaning is close. An agent using keyword search could also try new words, such as "charring", in a second search.

Memory plan: worked example and practice 3 min

A memory plan answers one question for each piece of information: where does it live, and how does it reach the context? Ask these in order.

  1. Is it needed on every call? Put it in the system prompt or tool definitions, and keep it short.
  2. Does another system hold the official, current value? Fetch it with a tool when needed.
  3. Is it part of a large body of text? Retrieve the relevant chunks.
  4. Does it matter only in this conversation? Keep it in the message list, and clear or summarize when it grows.
  5. Will it matter next visit, with no other home? Save a note under the student's ID.

Your turn 2: cost a request

"Am I cleared for the CNC router? If so, book Saturday at 10." The fixed parts are 1,500 tokens and the question 40. The model asks for the training record (result 100), then the calendar (result 200), then a booking (result 60), then answers. Each tool request is 50. Find the largest single input and the total input. Then price 2,000 such requests at a made-up rate of $1 per million input tokens.

First step: call 1 sends 1,500 + 40 = 1,540. Write down calls 2 onward yourself.

Show a solution

Call 2: 1,540 + 50 + 100 = 1,690. Call 3: 1,690 + 50 + 200 = 1,940. Call 4: 1,940 + 50 + 60 = 2,050. The largest input is 2,050. The total is 1,540 + 1,690 + 1,940 + 2,050 = 7,220 tokens. For 2,000 requests: 14,440,000 tokens, or $14.44. This leaves out output tokens, which you would price separately.

Summary 2 min

  • The context window is everything the model can refer to during a call, measured in tokens: instructions, tool definitions, messages, tool results and the reply.
  • Between steps, your program keeps the history and sends it again. Cost adds up across calls.
  • A crowded context costs more and can work worse. Clear old results, or compact with care.
  • Between sessions, the assistant knows only what your system saved and loads back. Official facts come from their own system.
  • Retrieval brings in the few relevant chunks, found by keywords, meaning or both.
