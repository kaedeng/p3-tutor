Context and memory: what your assistant can see and remember

By the end of this lesson you can write a memory plan for your makerspace assistant: what goes into each model call, what is saved between visits, how it finds a manual page, and roughly what that costs.

Objective O3: context and memory in an agent About 30 minutes Builds on: what a language model does, and the agent loop
Why this matters for you

At your design review, someone may ask, "Why not just give it all the manuals?" or "How does it know I'm trained on the laser cutter?" Your sponsor's budget depends on the answers too. This lesson gives you both the answers and the reasons.

Warm-up 2 min

Answer from memory before you open each solution. The effort is what makes it stick.

Recall 1

Where can a language model's knowledge come from when it writes a reply? Name both places.

Check your answer

From patterns learned in training, and from the text it is given as input. Today's booking calendar is in neither one unless your program puts it into the input. That second place is what this lesson is about.

Recall 2 (Python)

Your script builds a list with history.append(item). The script ends. You run it again. What is in history?

Check your answer

Nothing from last time. A variable lives only while the program runs. To keep data, you write it to a file or a database and read it back later. Agent memory rests on this same plain fact.

The context window 4 min

First, an example

A student types: "Is the laser cutter free Friday?" Your program does not send only that sentence. It sends something like this:

request = {
  "system":   "You help students at the makerspace...",
  "tools":    [check_calendar, search_manual, book_slot],
  "messages": [
    {"role": "user", "content": "Is the laser cutter free Friday?"}
  ]
}

The system prompt is the standing instructions your program sends: the assistant's job and rules. tools holds the descriptions of what it may ask for. messages is the conversation so far.

Tokens

The model reads all of this as tokens: the small pieces of text it works in. A token can be a word, part of a word, or a single character. One provider's glossary gives about 3.5 English characters per token for its newer models. The ratio varies, so use it only for rough estimates.

By that rule, a 700-character paragraph is about 700 ÷ 3.5 = 200 tokens.

The window

The context window is all the text the model can refer to while generating a reply, including the reply itself. It has a fixed maximum size, counted in tokens. The word context means the tokens actually given to the model for a call.

Think of a workbench. It has a fixed surface. Instructions, tool descriptions, parts and your half-built piece all share it. A shelf across the room may hold far more, but you can't work with something until it is on the bench.

According to one provider's documentation, all of these take up space:

  • the system prompt;
  • every message, including tool results, images and documents;
  • your tool definitions;
  • the output the model is writing.

What if you overfill it? The details depend on the API. In the one documented above, a request whose input is already too big is rejected with an error. On its newer models, a reply that runs into the limit while being written stops there.

Check yourself

Your assistant has 20 tool definitions. In one request the model uses none of them. Do they affect the context window?

Show the answer

"Yes, every definition takes space." Definitions are part of the input, used or not.

Between steps: the program carries the history 5 min

First, an example

The model asks for check_calendar. Your program runs it and gets "Friday 2–4 pm is free." Now the model has to be called again. What does that second call know?

Only what your program sends. The API in this example is stateless: it keeps no conversation for you from one call to the next, so you send the full conversation history each time. So the program keeps a list, adds to it, and sends all of it again.

Here is a sketch. call_model and run_tool stand for functions your team would write; real role names and formats differ between APIs.

messages = [{"role": "user", "content": question}]

for step in range(8):
    # send everything, every time
    reply = call_model(SYSTEM, TOOLS, messages)
    messages.append({"role": "assistant",
                     "content": reply})

    if reply["tool"] is None:
        break   # this is the final answer

    result = run_tool(reply["tool"], reply["args"])
    messages.append({"role": "tool",
                     "content": result})

That messages list is the assistant's memory between steps. It holds the question, each tool request and each result. If you forget to append the result, the next call has no idea what the calendar said.

Some services can store the transcript for you, and the same guide describes a beta feature of this kind. That changes who holds the list. The model still works from the text in its context.
A common mix-up

"The model remembers what we just said." It is tempting because chat apps feel continuous. But the app is resending the earlier turns behind the screen. Send a second call with only "And Saturday?" and the model cannot know you meant the laser cutter.

Why this changes your bill

Model APIs commonly price input and output tokens separately, per million tokens. Since the history is resent, early text is paid for again on later calls.

Worked example: counting input tokens

All sizes are made up but plausible. System prompt plus tool definitions: 1,500 tokens. Question: 50. The model searches a manual (request 60, result 1,200), then checks the calendar (request 60, result 140), then answers.

  1. Call 1 sends the fixed part and the question: 1,500 + 50 = 1,550.
  2. Call 2 sends all of that, plus the first request and result: 1,550 + 60 + 1,200 = 2,810.
  3. Call 3 sends all of that, plus the second request and result: 2,810 + 60 + 140 = 3,010.
  4. Total input billed: 1,550 + 2,810 + 3,010 = 7,370 tokens.

The largest single call was only 3,010 tokens. That number matters for fitting in the window. The 7,370 matters for cost. Output tokens are billed on top.

At an invented price of $1 per million input tokens, this request costs about $0.0074 in input. A thousand such requests cost about $7.37. Swap in your provider's real price.

Many APIs offer prompt caching, a discount for repeated text. It changes what you pay for those tokens, not whether they take up the window. This lesson's sums ignore it.
Check yourself

Fixed part: 1,000 tokens. Question: 100. The model makes one tool request (50 tokens), gets a result (850), then answers. How many input tokens are sent across both calls?

Show the answer

3,100: call 1 sends 1,100 and call 2 sends 2,000.

Keeping the context lean 3 min

First, an example

A student chats for 40 turns while planning a project. The history now holds six long manual search results, most about questions already settled.

It may still fit. But "fits" is not the same as "works well." As the token count grows, the model's ability to accurately recall information tends to fall. This is called context rot.

Position can matter too. In a 2023 study, "Lost in the Middle", the models tested often did best when the key fact was at the start or end of a long input, and much worse when it sat in the middle. Newer models may differ, so test yours.

The general aim is the smallest set of useful, high-signal tokens that gets the job done. "Smallest" does not mean "short at any price": leave out what doesn't help, and keep what does.

Your program has several tools for this:

TechniqueWhat the program doesMain risk
TrimmingDrops the oldest messagesAn early requirement vanishes
Clearing old tool resultsRemoves bulky raw results already usedA detail is needed again and must be fetched again
CompactionSummarizes the history and continues from the summaryThe summary loses something subtle but important

Compaction is like replacing pages of meeting chatter with the minutes. Anthropic's engineers describe clearing tool results as one of the safest, lightest forms of it, and warn that aggressive summarizing can lose critical context.

So decide what a summary must keep. For your assistant: the student's goal, the machine, chosen times, and any safety or training limit.

Check yourself

The 40-turn chat is getting large. Which item is the best one to remove first?

Show the answer

The old search result. It is large, used up and easy to get back. The goal and the rules still steer every step.

Between sessions: notes as memory 5 min

First, an example

On Monday, Priya says, "I usually build in the evenings, and I'm making a drone frame." On Thursday, Priya opens a new chat: "Book me my usual kind of slot."

A session here means one visit or conversation. Thursday's session starts with a fresh message list. Unless your program saved something on Monday and loads it now, "usual" means nothing.

Two terms name the difference. Short-term memory covers one conversation thread. Long-term memory keeps information across different conversations or sessions. A program can save short-term history too, so that an interrupted chat can be resumed.

Notes in Python

The simplest version uses things you already know: a dict and a JSON file for each student.

import json, os

def load_notes(student_id):
    path = f"notes/{student_id}.json"
    if not os.path.exists(path):
        return {}
    with open(path) as f:
        return json.load(f)

def save_note(student_id, key, value, today):
    notes = load_notes(student_id)
    notes[key] = {"value": value, "saved_on": today}
    os.makedirs("notes", exist_ok=True)
    with open(f"notes/{student_id}.json", "w") as f:
        json.dump(notes, f)

Monday: save_note("priya", "preferred_time", "evenings", "2026-11-23"). Thursday: call load_notes("priya") and put the result into the context. Now the model can read "evenings."

A common mix-up

"It's saved, so the assistant knows it." A note in a file is like a sticky note in a closed drawer. It affects a reply only after the program, or a tool the model asks for, brings its text into the context.

Who writes the notes?

Your code can save fixed facts itself. Or you can give the model a tool for writing notes. Anthropic calls the habit of an agent writing notes outside the context window and pulling them back later structured note-taking. It helps within one long task as well as across sessions, for example as a running to-do list.

The model still only asks. In one provider's memory tool, the model requests file operations and your application carries them out and stores the files.

Notes can be written during the chat, which is immediate but adds delay and work. They can also be written afterwards as a separate job, which means a new chat might start before the note exists.

What deserves to be saved?

Here are rules of thumb I suggest for your design:

  • Save stable, useful things: preferred times, current project, preferred units.
  • Look up live things that change or must be correct: free slots, training status. Ask the official calendar or training database each time.
  • Don't save secrets or personal details the assistant doesn't need.
  • Date every note, and let students correct or delete notes.

Safety is your program's job. The memory tool documentation advises checking every file path, limiting file size, removing stale files and filtering sensitive data. In the code above, take student_id from the login, never from the chat, so one student can't open another's notes.

Check yourself

Which of these is the best fit for a saved long-term note about a student?

Show the answer

The evening preference. It stays true across visits and helps the next one.

Retrieval: finding the right page 5 min

First, an example

Suppose your makerspace has six manuals of 150 pages each. Anthropic equates 200,000 tokens with about 500 pages, roughly 400 tokens per page. So:

6 × 150 × 400 = 360,000 tokens for all the manuals.

Sent on each of three calls, that is over a million input tokens, or about $1.08 per question at our invented price. Three relevant passages of 400 tokens each are only 1,200 tokens.

Retrieval means searching stored material and bringing back just the relevant parts. Adding those parts to the model's input so it can answer from them is called retrieval-augmented generation, or RAG. It works like an open-book exam: you look up the page instead of carrying the whole shelf in your head. The idea was named in a 2020 research paper; today the term also covers simpler setups that train nothing.

The pipeline

First, ahead of time, split each manual into chunks: passages usually no more than a few hundred tokens. Then, for each question, search the chunks and send the best few to the model.

Two ways to search

Keyword search matches words and phrases. A widely used scoring method is BM25. It is good for exact terms such as an error code.

Embedding search turns each chunk and the question into lists of numbers that represent meaning, then finds the closest ones. It can match different words with similar meanings. Systems often combine both.

Worked example: a toy keyword search 
def search_manual(query, chunks, k=1):
    words = set(query.lower().split())
    def score(chunk):
        found = set(chunk.lower().split())
        return len(words & found)   # shared words
    return sorted(chunks, key=score,
                  reverse=True)[:k]

Three invented chunks:

  • A: "Laser cutter materials: maximum plywood thickness 6 mm"
  • B: "Laser cutter safety: never leave a job unattended"
  • C: "CNC router materials: clamp plywood flat"
  1. Query "maximum plywood thickness": A shares three words, B none, C one. A wins.
  2. Query "thickest plywood allowed": A shares only "plywood", and so does C. It's a tie, although a person sees that A answers it. This code returns A only because A is listed first.

"Thickest" and "thickness" are different strings to this code. That gap is what better text processing or embedding search tries to close. Real keyword search is smarter than this toy, for instance in how it weighs words.

Chunks can lose their meaning

Imagine the chunk "Replace it every 40 hours." Replace what, on which machine? Cutting a document apart can strip away the context a passage needs. A simple fix is to store each chunk with its machine, section title and page. Anthropic's version adds a short generated explanation to every chunk before indexing.

Search as a tool

In your agent, search_manual can be a tool. The model asks for it when needed and can search again with better words. This is just-in-time retrieval. The alternative is to search up front, before the model's first call. Up front saves a step; searching during the loop is more flexible but slower. You can mix them.

Do you always need retrieval? No. Anthropic suggests that a knowledge base under about 200,000 tokens can simply go into the prompt whole, if the model's window holds it, ideally with caching. With a small budget, still do the cost sum first.

Check yourself

A student asks how to "halt the machine in an emergency." The manual only says "E-stop: press the red button." Keyword search finds nothing useful. What is the most sensible fix?

Show the answer

Add search by meaning (or synonyms). The failure is a mismatch of words, so fix the search.

Worked example and your turn 4 min

A memory plan, as we'll use the term, sorts each piece of information by where it lives and when it reaches the model. Ask four questions:

  1. Is it needed on every call? Put it in the fixed context.
  2. Did it arise during this task? Keep it in the message history, and trim it once it stops helping.
  3. Does it change, or must it be correct? Fetch it live from its official source.
  4. Is it stable and useful later? Save a note. Is it large reference text? Retrieve pieces of it.
Worked example: one real request

Sam asks: "Can I cut 5 mm plywood on the laser cutter Thursday evening?"

Plywood limitManual chunkssearch_manual result
Thursday's free slotsBooking calendarcheck_calendar result
Sam's training statusTraining databasecheck_training_record result

Between steps: each tool request and result joins the history. Between sessions: only useful, stable notes carry over. The calendar and training record are read again next time.

Cost control: return a few chunks, not whole chapters. Return only Thursday evening from the calendar. In a long chat, clear old search results.

Your turn

A week later, Sam asks: "The 3D printer jammed again, same filament as last time. How do I clear it?"

Sort these: (a) which filament Sam used, (b) the unjamming steps, (c) what Sam has already tried during this chat. For each, say where it lives and how it reaches the model. Then name one thing that could go wrong.

Started for you: (a) must have been saved last week, because this is a new session. Now finish it.

Show a solution

(a) Filament: a dated saved note (or a past booking record), loaded at the start or fetched by a tool. Confirm it with Sam, since it may have changed. If nothing was saved, the assistant must ask, not guess.

(b) Steps: in the printer's manual. Retrieve the relevant chunks with the search tool, labeled with the printer model.

(c) Already tried: in the message history, resent with each call. If you compact the chat, the summary must keep it.

Possible failures: search returns steps for a different printer; the note is stale; a summary drops a tried step and the assistant suggests it again.

One step further: cost

Your teammate wants search_manual to return 10 chunks of 400 tokens instead of 3. The search happens on call 1, and calls 2 and 3 follow. How many extra input tokens does one request send?

Show a solution

Extra per result: 7 × 400 = 2,800 tokens. The result first appears in call 2 and is resent in call 3, so 2 × 2,800 = 5,600 extra input tokens. More chunks might raise the chance of including the answer, so measure that gain before paying for it.

Summary 2 min

  • The context window is a limited space, in tokens, shared by instructions, tool definitions, history, results and the reply.
  • Between steps, the history is resent, so input cost adds up over calls. Keep it lean by clearing, trimming or compacting.
  • Between sessions, only what is saved survives, and it helps only once loaded into context.
  • Retrieval brings the relevant pieces of large material into context when needed.
  • Facts that change or must be right come from their official source, live.

Say it in your own words: without scrolling up, explain to a teammate how your assistant could "remember" a student on their next visit, when the model itself keeps nothing from the last one. Include save, load, and one thing you would not save.
