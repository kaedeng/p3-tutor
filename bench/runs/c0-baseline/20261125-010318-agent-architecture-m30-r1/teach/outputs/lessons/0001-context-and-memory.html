Context and memory: what your assistant sees, and what it keeps

By the end of this lesson you can plan, for a real makerspace request, what goes into the model's input, what gets saved for later, and how the right manual page gets found.

Objective O3: context and memory in an agent About 30 minutes Builds on: what a language model does, and the agent loop
Why this matters for you

Your assistant has to answer from long manuals and know things about a student who visited last week, on a small budget. Those are three design decisions: what the model reads, what your program saves, and how it searches. Your design review will ask about all three.

Warm-up 1 min

Answer from memory before you open each one.

Recall 1

How does a language model produce its reply?

Check your answer

One token at a time, each one predicted as a likely next piece, using patterns learned in training. Today you will see why counting those tokens matters.

Recall 2

The makerspace changed its opening hours last week. The model's training ended before that. How could it still answer correctly?

Check your answer

The new hours have to be in the text the model is given. It knows only its training plus its input. Almost everything in this lesson follows from that one fact.

What the model sees on one call 3 min

A student types: "Can I cut 6 mm acrylic on the laser cutter?"

Your program does not send only that sentence. It sends something more like this (simplified, with invented contents):

SYSTEM: You are the makerspace assistant. Answer from
        the manuals. Never guess a safety setting.
TOOLS:  search_manuals(query): find manual passages
        check_calendar(machine, date): list bookings
USER:   Can I cut 6 mm acrylic on the laser cutter?

The first part is the system prompt: standing instructions your program includes to set the assistant's job and rules.

The second part holds the tool definitions: text that tells the model which tools exist, what each does and what inputs it takes.

The third part is the student's message.

All of this text together is the model's context for this call. The context window is the space that holds it: all the text the model can refer to while generating a response, including the response itself (context windows documentation).

So the window holds your instructions, your tool definitions, every message so far, every tool result and any attached documents. The reply being written needs room there too (same page).

Think of an open-book exam with one small desk. Your training is what you studied. The desk is the context window. A book left on the shelf does not help until someone puts the right page on the desk.

Check yourself

You add three more tools to the assistant. A student then asks a question that needs none of them. What happens to the context on that call?

Show the answer

It grows. Tool definitions are part of the input on every call that offers those tools, used or not.

Tokens: the limit and the bill 4 min

The window is not measured in words or pages. It is measured in tokens.

A token is a small unit of text that the model reads and writes. It can be a whole word, part of a word or a single character (glossary).

How much text is one token? It depends on the model. One provider's glossary gives about 3.5 English characters per token for some of its models, and says its newer ones produce about 30% more tokens for the same text (source). For real planning, count with the tools for your model.

The limit

Each model has a maximum window size. As one example, a provider lists models with 200,000 tokens and others with up to 1 million (documentation).

If your input alone is bigger than the window, the request fails with a "prompt is too long" error in that provider's API. If the reply runs into the limit while being written, it can stop early (details).

The bill

Input tokens are what you send. Output tokens are what the model writes back. Providers can charge different prices for each, quoted per million tokens (pricing example).

Tool definitions and tool results are counted in the tokens you pay for (same page).

Worked example: the cost of one call

To keep the arithmetic easy, this lesson uses invented prices: $1 per million input tokens and $5 per million output tokens. A call sends 2,000 input tokens and gets 300 back.

  1. Input: 2,000 ÷ 1,000,000 × $1 = $0.002.
  2. Output: 300 ÷ 1,000,000 × $5 = $0.0015.
  3. Add them: $0.0035 for this call.
  4. Scale it: 1,000 such calls cost $3.50.

Notice step 4. A tiny per-call cost is what you multiply by every student, every question and every step.

Check yourself

Using the same invented prices, what does a call with 4,000 input tokens and 200 output tokens cost?

Show the answer

$0.0050: input 4,000 × $1 per million = $0.004, plus output 200 × $5 per million = $0.001.

Between steps 4 min

Now the student asks: "Can I cut 6 mm acrylic, and is the laser cutter free Friday?"

The assistant checks the calendar, then searches the manual, then answers. How does the model still know the calendar result by the time it writes the answer?

Not by remembering it. A model API of the usual kind is stateless: it keeps nothing from one request for the next, so your program sends the full conversation history each time (Messages API documentation).

Your program keeps that history, usually as a list. Here is the idea in Python-like code. The function names are made up.

messages = [{"role": "user", "content": question}]

for step in range(MAX_STEPS):
    # one model call: it gets everything again
    reply = call_model(SYSTEM_PROMPT, TOOLS, messages)
    messages.append(reply)

    if reply["tool"] is None:
        break                      # final answer

    # YOUR code runs the tool, not the model
    result = run_tool(reply["tool"], reply["args"])
    messages.append({"role": "tool", "content": result})

Real APIs use their own message formats, but the pattern is the point. The model writes a request. Your code runs the tool and appends the result. The next call receives the longer list.

Here is what that costs, with invented sizes. The prompt, tools and question total 1,250 tokens. Each tool request is 50. The calendar result is 200, and the manual result is 2,000. The final answer is 300.

CallInput tokensOutput tokens
1: asks for calendar1,25050
2: asks for manual1,250 + 50 + 200 = 1,50050
3: writes answer1,500 + 50 + 2,000 = 3,550300
Total6,300400

At the invented prices: $0.0063 for input plus $0.0020 for output, so $0.0083 for the request.

The last call holds 3,550 tokens, but you paid for 6,300 input tokens. Early text is paid for again on every later step.

Prompt caching is a discount some providers offer for input that repeats from an earlier request. One provider prices most cached reads at a tenth of the normal input price, while writing to the cache costs extra (pricing). It lowers the price, but the text still occupies the window.

Some services will store the history for you, so your program sends only the new message (one beta example). That changes who holds the list. Do not assume it makes the history free: one provider states that earlier input in a stored chain is still billed (conversation state guide).

A common mix-up

"The model remembers what it did earlier." It is tempting because a chat feels like talking to one person who is listening the whole time.

What actually happens: an app or program saves the text and puts it back in front of the model. Delete the calendar result from messages before call 3, and the model has no calendar result to use. It might even invent one.

Check yourself

A bug makes your program send only the newest message on each call. The system prompt and tools are still sent. After the manual search, what goes wrong?

Show the answer

The model gets a manual result with no question attached, and no calendar result. Keeping the history is your program's job.

When the context gets long 3 min

Picture a student planning a project over 40 messages, with several manual searches along the way. The list keeps growing.

Two problems arrive. You already know the first: cost rises, and eventually the input will not fit.

The second arrives earlier. As the token count grows, the model gets worse at accurately recalling what is in its context. This is called context rot (documentation). It is a gradual decline, not a sudden cliff (context engineering article).

So the goal is not to fill the window. It is to send the smallest set of useful tokens that gets the job done. Choosing and maintaining that set is called context engineering (same article).

Think of a workbench. Keeping every offcut on it does not help you find the drill bit.

Your program has three basic ways to tidy up:

TechniqueWhat it doesWhat you risk
TrimmingDrops older messagesLosing an early requirement
Clearing tool resultsRemoves bulky old resultsNeeding to fetch one again
CompactionSummarizes the history, then continues from the summaryThe summary leaving out something that matters later

The article calls clearing old tool results the lightest form of compaction. For summaries, it advises first making sure the important details survive, and only then cutting the extra.

Worked example: a good summary

Forty messages about building a lamp become:

"Goal: acrylic lamp base. Material: 6 mm clear acrylic. Student wants a Friday slot, not yet booked. Open question: engraving depth."

It keeps the goal, the facts, what is unfinished and what is undecided. It drops greetings and old search results.

Check yourself

A 3,000-token manual result from 30 messages ago is no longer being discussed. What is a sensible move?

Show the answer

Clear the old result and keep a short pointer to where it came from. You save tokens and can still get it back.

Between sessions: notes as memory 4 min

A session (many tools say thread) is one continuous conversation. On Monday, Sam says, "I'm making a plywood phone stand." On Thursday, Sam opens a new chat.

A new session starts with a new message list. If your program saved nothing and loads nothing, the model has no trace of Monday.

In agent design, memory comes in two spans (LangChain memory overview):

  • Short-term memory follows the ongoing conversation, mainly its message history. It belongs to one thread. It can be stored so the same thread can be resumed.
  • Long-term memory holds information kept across sessions, such as facts about a user. Any later thread can recall it.

Notes

The simplest long-term memory is a note. With structured note-taking, an agent writes notes that are stored outside the context window and brought back in later (article). A to-do list or a notes file counts.

For your assistant, that could be a small JSON record:

{"student": "sam",
 "project": "plywood phone stand",
 "saved_on": "2026-11-23"}
# at the start of a new session
notes = load_notes(student_id)   # your storage
system = SYSTEM_PROMPT + "\nSaved notes: " + json.dumps(notes)

Who writes the note? The model can request it through a tool such as save_note, and your code does the saving. Writing during the chat makes the memory available at once, but adds delay and splits the model's attention. Writing afterwards, as a background task, avoids that delay, but other sessions may not see the update in time (tradeoffs).

What to save

The same overview describes three kinds of long-term memory. The examples are mine:

KindHoldsMakerspace example
SemanticFactsSam is working on a phone stand
EpisodicPast eventsSam's last cut did not go through
ProceduralRules for doing the taskAlways confirm the date before booking

Saved memories can go stale, and keeping them updated or deleted correctly is tricky (overview). My design advice: date each note, save only what a later visit will use, keep each student's notes separate, and tell students what you store.

A common mix-up

"It will learn our students as they chat." It is tempting because people do learn this way. But calling the model, as you will here, is not training it. If a later session knows something, find the code or service that saved it and put it back into the input.

Check yourself

A saved note says Sam is not yet trained on the laser cutter. Sam says they passed the training yesterday and wants to book it. What should the assistant do?

Show the answer

Check the official record with a tool. For anything that controls safety or access, look it up fresh.

Finding the page: retrieval 5 min

Suppose your manuals add up to 200,000 tokens. A student asks about one setting on one machine.

Retrieval means searching an outside collection and bringing only the relevant pieces into the context. When those pieces help the model write its answer, the method is called retrieval-augmented generation, or RAG (glossary).

It works like using a book's index. You look up the topic and open two pages, instead of rereading the book.

A basic setup has these steps (retrieval article):

  1. Ahead of time, split each manual into chunks, passages usually no longer than a few hundred tokens.
  2. Build a search index over the chunks.
  3. When a question arrives, search the index and pick the best few chunks.
  4. Add those chunks to the model's input with the question.

Two ways to search

Keyword search matches the words themselves. A common ranking method is called BM25. It is strong on exact terms such as part numbers and error codes.

Embedding search matches meaning. An embedding is a list of numbers computed from a text, so that texts with related meanings can be found near each other. It can connect "my cut didn't go through" with a passage on "insufficient laser power". It can also miss an exact code.

Many systems combine the two (how and why).

A trap: the orphan chunk

Imagine a chunk that says only: "Set power to 60% and speed to 15." For which machine and material? The splitting cut that off. Keep the manual name and section heading with each chunk. The article goes further and adds a short generated description to every chunk before indexing it.

Who does the searching?

Your program can search before calling the model. Or the model can ask for a search through a tool, and open more as it learns what it needs. The second style is just-in-time retrieval: keep light references, such as file names or page numbers, and load content only when needed. It can be slower, and an agent can waste context chasing dead ends. A mix of both is also possible (article).

Do you need retrieval at all?

Not always. A 2024 article says that a collection under about 200,000 tokens (roughly 500 pages) can simply go into the prompt whole. But check your budget:

Manual text per callCost per call1,000 calls
Everything: 200,000 tokens$0.20$200
5 chunks of 400: 2,000 tokens$0.002$2

These are invented prices, manual text only, with no caching. Caching would narrow the gap. Retrieval has its own setup costs, and it can fetch the wrong chunk. Test both with real student questions.

Check yourself

A student asks what fault code E-417 on the CNC router means. Which approach is most likely to find the exact passage?

Show the answer

Keyword search for the exact code. A combined search would also include it.

Worked example and practice 4 min

Put the pieces together. For any request, ask five questions: What is always sent? What is loaded from memory? What is retrieved or looked up? What stays out? What is saved afterwards?

Worked example

On a new visit, Sam asks: "What laser settings should I use for my phone stand?"

  1. Always sent: system prompt (500 tokens) and tool definitions (700). The model needs its rules and options.
  2. From memory: Sam's notes (150), which say the project is a plywood phone stand. Without this, "my phone stand" means nothing. Confirm the thickness if the notes lack it.
  3. The question: 50 tokens.
  4. Retrieved: four chunks on laser settings for plywood, 400 tokens each (1,600), with their headings.
  5. Left out: other students' notes, old chat transcripts and the rest of the manual. They add cost and distraction, and other students' notes are private.
  6. Estimate: 500 + 700 + 150 + 50 + 1,600 = 3,000 input tokens, about $0.003 at our invented price. This is the call that writes the answer, ignoring the small search request before it.
  7. Saved afterwards: anything new that a later visit needs, such as the thickness, with today's date.
Your turn

Later, Sam writes: "The 3D print I started Monday failed the same way again. What should I try?"

Sizes: system prompt and tools 1,200 tokens; notes 120; question 40; each manual chunk 400. You plan to use three chunks.

The first step is done: the prompt and tools are always sent. On paper, decide:

  1. What must have been saved on Monday for "the same way" to make sense?
  2. What would you search for?
  3. What stays out?
  4. How many input tokens is the answering call?
  5. What do you save now?
Show a solution

1. A dated note of the event: the printer, the material and how the print failed (an episodic memory). If it was never saved, the assistant should ask Sam, not guess.

2. Troubleshooting passages for that printer and that failure, using the words from the note.

3. Other students' notes, unrelated manuals and full old transcripts.

4. 1,200 + 120 + 40 + 3 × 400 = 2,560 input tokens.

5. That it failed again, the date and what was suggested, so the next visit does not repeat the same advice.

Summary 2 min

  • The context window is everything one model call can read and write, measured in tokens.
  • Between steps, your program keeps the history and sends it again. That costs tokens each time.
  • Long contexts cost more and are recalled less accurately. Trim, clear or summarize with care.
  • Between sessions, only what is saved and loaded again carries over.
  • Retrieval brings in the few passages a question needs.
