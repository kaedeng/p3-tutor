What the assistant can see: context, memory and retrieval

By the end of this lesson you can take one request to your makerspace assistant and decide, for each piece of information, whether to send it, carry it, save it or fetch it, and estimate what that choice costs.

Objective O3: context and memory in an agent About 30 minutes Builds on: what a language model does, and the agent loop
Why this matters for you

At your design review you need to say what the assistant keeps in front of the model, what it saves between visits, and how it finds the right page in a long manual. Each of those choices also changes your model bill.

Warm-up 2 min

Answer from memory before you open each answer. The effort is what makes it stick.

Recall 1

This semester the makerspace changed its opening hours, after the model was trained. From what source could the model get the new hours?

Check your answer

Only from the text it is given. A model knows what it learned in training plus what is in its input. The new hours are not in training, so something has to put them in the input. Today is about that "something".

Recall 2

Say the agent loop out loud, starting with "The model is given a goal and some tools…"

Check your answer

The model is given a goal and some tools. It asks for an action. The action is carried out. The result goes back to the model. This repeats until the model gives a final answer or a limit is reached. Today you will look closely at what "goes back to the model" really means.

What the model sees: the context window 5 min

Start with one request

A student types: "Is the laser cutter free Friday at 3?" Your program does not send only that sentence. It builds a bigger package and sends the whole thing to the model. In Python terms, it looks roughly like this (a simplified sketch, not a real library):

request = {
    "system": "You help students at the makerspace. ...",
    "tools": [calendar_description, manual_search_description],
    "messages": [
        {"role": "user",
         "content": "Is the laser cutter free Friday at 3?"}
    ],
}
reply = call_model(request)   # stand-in function

There are three parts. The system prompt is your standing instructions. The tool descriptions say what each tool does and what inputs it takes. The messages are the conversation so far, held in an ordinary list.

Everything the model can read for this reply is the context. If a fact is not in there and was not learned in training, the model does not have it.

Tokens: the unit of size

You know a model writes one token at a time. It reads in tokens too. A token is a small chunk of text: a word, part of a word, or a single character. As a rough guide, one provider says a token is about 3.5 English characters for its newer models. Other models split text differently.

So the student's 37-character question is about 37 ÷ 3.5, or roughly 11 tokens. A full page of a manual is much bigger, around 400 tokens (using an estimate of 200,000 tokens for about 500 pages).

The window: the size limit

The context window is the maximum amount of text, counted in tokens, that the model can work with in one call. It covers all the text the model can reference, including the reply it is writing.

Think of a workbench. Whatever you are using must fit on the bench, and you need some clear space to do the work. The cupboard across the room may be full of useful things, but you cannot use them until you bring them over.

According to one provider's documentation, the system prompt, every message (tool results included), the tool descriptions and the model's output all count. If the input alone is too big, that provider's service rejects the request with an error.

Why tokens cost money

Model services commonly charge per million tokens, with separate rates for input and output. Input tokens are what you send. Output tokens are what the model writes. A bigger context means a bigger bill on that call, even if the model never needed the extra text.

Between steps: who does the remembering 4 min

Watch the list grow

Now the student asks: "Is the laser cutter free Friday, and what material is banned on it?" One step here means one call to the model, plus any tool run it asks for. Assume the system prompt and tool descriptions total 1,500 tokens, and the question is 100. All sizes are made up.

  1. Call 1. Input: 1,600 tokens. The model asks for the calendar tool (a request of about 50 tokens).
  2. Your program runs the tool, gets a 300-token result, and appends both the request and the result to the list.
  3. Call 2. Input: 1,600 + 50 + 300 = 1,950. The model asks to search the manual.
  4. Your program runs the search, which returns 2,000 tokens of manual text, and appends again.
  5. Call 3. Input: 1,950 + 50 + 2,000 = 4,000. The model writes the final answer.
messages = [question]
for step in range(MAX_STEPS):
    reply = call_model(system, tools, messages)
    messages.append(reply)
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)
    messages.append(result)   # this is the "memory"

The general idea: the model call is stateless

Stateless means that nothing from one call is carried into the next by the call itself. One provider says it directly: its Messages API is stateless, so you always send the full conversation history.

So how does call 3 "know" what the calendar said? Your program kept it in messages and sent it again. This running record is the agent's short-term memory: the history of one ongoing conversation, kept by the software around the model. A real system may also save it to a database so a paused conversation can resume.

Some services offer to store the conversation on their side so you send only the new part (one offers this as a beta feature). That changes where the list is kept. Software is still doing the keeping.

An everyday version: you phone a help desk where a different person answers every time. Each one is capable, but knows nothing about your earlier calls. It works only because there is a ticket file, and each new person reads it first. Your messages list is the ticket file.

The bill adds up across calls

Look at what you paid to read. The largest call was 4,000 tokens, but the total input was 1,600 + 1,950 + 4,000 = 7,550 tokens. The instructions and the question were sent three times.

Check yourself

To save money, a teammate's program sends only the newest tool result on call 3. It uses an ordinary stateless call. What happens?

The model cannot tell what was asked. Anything it needs on call 3 must be in call 3's input.

When the context grows: cost and quality 4 min

A long session, with numbers

Suppose a student works through a long troubleshooting chat. The first call has 1,600 input tokens, and each later call has 1,000 more than the one before.

Calls so farInput on the last callTotal input paid for
11,6001,600
1010,60061,000
2020,600222,000

Twice as many calls cost more than three times as much input. Each call is larger, and there are more of them. This is why a step limit protects your budget as well as your patience.

Some services discount text that repeats from call to call, which is called prompt caching. It can lower the price, but cached text still fills the window.

Quality drops too

A crowded bench makes it harder to find the right tool. Models have a similar problem. As the token count grows, accuracy and recall can degrade, which is called context rot.

Position can matter as well. A study of long inputs found that the models it tested often did best when the key information was near the beginning or end, and much worse when it was in the middle. Newer models may differ, so test your own.

A common mix-up

"A bigger window solves it. Just send everything." It is tempting because the error goes away. But you still pay for every token on every call, and more context is not automatically better. A window is a limit, not a target. Aim for the smallest set of useful, relevant tokens that gets the job done.

Ways to keep it small

Choosing what goes into the context on each call is called context engineering. Your program can do it in several ways.

MethodWhat the program doesWhat to watch
Clear old tool resultsRemoves bulky raw output that has already been usedA later step may need it again
Trim historyDrops stale messagesAn old message may still matter
CompactionSummarizes a nearly full conversation and continues from the summaryA summary can lose details
Notes outside the windowWrites key facts to storage and reads them back when neededNotes must be correct and findable

Anthropic's engineering guide calls clearing tool results one of the lightest-touch forms of compaction, and warns that summarizing too aggressively can lose subtle but important details. Removing stale information is also a standard answer to histories that do not fit.

Check yourself

Show the answer

Old raw search results that were already acted on. The request and the newest result are still needed.

Between sessions: saved memory and notes 5 min

Maya comes back

On Tuesday, Maya tells the assistant, "I'm building a drone frame, and please send reminders by email." On the next Monday, in a new chat, Maya types: "Book the printer for my project."

A session is one conversation or visit. Monday's session starts with a fresh messages list. Unless your program saved something on Tuesday and loads it now, the model has no idea what "my project" means.

Here is the smallest thing that works. During or after Tuesday's session, the program writes to a file:

{
  "student_1042": [
    {"date": "2026-11-17",
     "note": "Building a drone frame"},
    {"date": "2026-11-17",
     "note": "Wants reminders by email"}
  ]
}

On Monday, it reads Maya's entry and puts those lines into the context:

import json

def build_system(student_id):
    with open("memory.json") as f:
        notes = json.load(f).get(student_id, [])
    return INSTRUCTIONS + "\nSaved notes: " + json.dumps(notes)

The general idea: long-term memory

Long-term memory is information stored outside the context that can be recalled in other conversations, at any later time. It might be a file, a database table or a searchable store. It helps the model only when some of it is copied into the context.

Notes are one simple form. The agent regularly writes notes to storage outside the context window and pulls them back later. A to-do list or a notes file works. Notes also help inside one long task, because they survive trimming and compaction.

A common mix-up

"The model will remember Maya from last time." It is tempting because some chat apps do seem to remember you. That is a feature built around the model: for example, an app can give the model a tool for saving memories, which the app stores. In your assistant, nothing is remembered between sessions unless your design saves it and loads it back.

What deserves saving

Ask three questions. Will it matter in a later session? Will it still be true then? Is there already an official place that holds it?

InformationWhere it livesHow the model gets it
Assistant's rulesYour programSent on every call
Current chat and tool resultsHistory listRe-sent, trimmed as needed
Maya's preferences and projectLong-term memoryLoaded for Maya's sessions
Training statusOfficial training recordLooked up with a tool
Free time slotsBooking calendarChecked with a tool when needed
Machine manualsDocument storeRelevant passages retrieved

Training status is a good test. It matters between visits, so the assistant must "remember" it in some sense. But a staff-maintained record already holds it. A second copy in chat memory could drift out of date, or contain a student's unproven claim. Look it up at the source.

Who writes the memory, and when

The agent can save a note while it handles the request, or a separate background task can do it afterwards. Saving during the request makes the note available at once but can slow the reply. Saving in the background avoids that delay, but you must decide when it runs, or a new session may miss recent facts.

Either way, treat memory as data you are responsible for. Date each note, let newer facts replace older ones, keep each student's notes separate, and store no more than the assistant needs.

You may see long-term memory sorted into semantic (facts), episodic (past experiences) and procedural (instructions). Maya's preference is a semantic memory. The labels are a thinking aid; your design does not need three databases.

Retrieval: finding the right page 5 min

One question, a long manual

A student asks: "What does error E-14 mean on the laser cutter?" (The error code is invented.) The answer is on one page of a long manual. You would not photocopy every manual in the building for them. You would check the index and open that page.

Retrieval means searching stored material and bringing only the relevant pieces into the context. When a model then answers using them, the pattern is called retrieval-augmented generation, or RAG.

The basic recipe

A common design has these parts (described here):

  1. Ahead of time, split each manual into chunks: short passages, usually no more than a few hundred tokens. Keep the manual name and page number with each one.
  2. Ahead of time, build what the search needs, such as a list of which chunks contain which words (the two kinds of search are explained below).
  3. When a question arrives, search, and keep the best few chunks. That number is often called top-k.
  4. Put those chunks into the context with the question, and call the model.

Two ways to search

Keyword search matches the actual words. Embedding search (or semantic search) turns each text into a list of numbers, an embedding, so that texts with similar meaning can be found even when the words differ.

Here is a deliberately simple keyword search:

def keyword_search(question, chunks, k=2):
    words = set(question.lower().split())
    def score(chunk):
        text = chunk["text"].lower()
        return len(words & set(text.split()))
    return sorted(chunks, key=score, reverse=True)[:k]

Work it through with the question what does error e-14 mean:

Chunk textShared wordsScore
p.12: "clean the lens after each job"none0
p.40: "what the error light does during warm up"what, does, error3
p.88: "error e-14 means the lid sensor is open"error, e-142

The wrong page wins, because ordinary words like "what" and "does" count as much as the error code. ("Means" and "mean" also fail to match.) With k=2 the right page still gets in; with k=1 it would be missed.

A standard, better keyword method called BM25 scores more carefully, which helps stop common words from dominating. It is especially useful for exact identifiers and technical terms. Embedding search helps when a student writes "the cutter won't start" and the manual says "unit fails to power on". Using both and merging the results is called hybrid search.

Before the call, or on demand

Your program can search before calling the model. Or you can offer search as a tool, so the agent looks things up just in time, reads the result, and searches again if needed. Looking things up during the run keeps the context lean, but is slower than fetching in advance, and a poorly guided agent can waste tokens on dead ends. Mixing the two is a reasonable design.

You may not need search at all for a small collection. One guide suggests that under about 200,000 tokens (about 500 pages), you can put the whole thing in the prompt, using prompt caching to reduce the cost. For your small budget, calculate it. Take 480 pages at 400 tokens each, 192,000 tokens, and an invented price of $1 per million input tokens, with no caching:

Design (manual text only)Tokens per requestCost of 100 requests
All manuals, on 4 calls4 × 192,000 = 768,000$76.80
Five 300-token chunks, on 3 calls3 × 1,500 = 4,500$0.45
A common mix-up

"Once retrieval has run, the model has learned the manual." Retrieval only places some text in the context. The model is not retrained, and it sees only the chunks you sent. If search picks the wrong ones, the model may still answer confidently. Tell it to cite the page and to say when the passages do not contain the answer, then check both behaviors in testing.

Check yourself

A student types an exact part number, "LC-4471-B". Which search is the surest way to find passages containing it?

Show the answer

Keyword search such as BM25, which is strong on exact identifiers. In a real system you might run it alongside embedding search.

Worked example and practice 4 min

Worked example

Sam asks: "Can I use the CNC router Friday at 3, and which bit should I use for plywood?" The system prompt and tool descriptions are 1,500 tokens and the question is 100. Sam has a 50-token saved note: "usually needs 90 minutes". The router manual is 60 pages.

  1. Send every time: instructions, tool descriptions, the question. The model needs the rules and the task on each call.
  2. Load from memory: Sam's note. It affects how long a slot to check.
  3. Fetch fresh: the calendar (300 tokens) and the training record (100). Both can change, and both have an official source.
  4. Retrieve: three 300-token chunks about bits, 900 tokens, instead of 60 pages × 400 = 24,000.
  5. Add up the input. Each tool request is 50 tokens.
    Call 1: 1,500 + 100 + 50 (the note) = 1,650.
    Call 2: 1,650 + 50 + 300 = 2,000.
    Call 3: 2,000 + 50 + 100 = 2,150.
    Call 4: 2,150 + 50 + 900 = 3,100.
    Total: 8,900 tokens.
  6. Compare: with the whole router manual added at call 4 instead, that call is 26,200 and the total is 32,000, about 3.6 times as much.
  7. Save afterwards: nothing new here. The calendar result will go stale, and Sam's note already exists.
Your turn

A week later, Sam says: "Book the router again, same day and time as last week. And from now on, remind me the day before."

The system prompt and tool descriptions are still 1,500 tokens. The question is 100. The loaded memory is now 200 tokens and includes last week's booking. The agent calls three tools in order: calendar (300-token result), training record (100), then booking (100). Each request is 50 tokens, and then it writes the answer.

Decide, on paper:

  1. What comes from memory, and what must be checked fresh? (Start: "same day and time" refers to last week, so that detail comes from memory.)
  2. Does the manual need searching?
  3. What is the total input across all calls?
  4. What, if anything, should be saved?
Show a solution

1. From memory: last week's day and time. Fresh: whether this Friday's slot is free, and whether Sam's training is still valid.

2. No. Nothing in the request asks about how the machine works.

3. Call 1: 1,500 + 100 + 200 = 1,800. Call 2: 1,800 + 50 + 300 = 2,150. Call 3: 2,150 + 50 + 100 = 2,300. Call 4: 2,300 + 50 + 100 = 2,450. Total: 8,700 tokens. Four calls, because three ask for tools and one writes the answer.

4. The reminder preference, because it is meant to last. The new booking belongs in the booking system; a short dated note about it is useful if students often say "same as last time".

Summary 1 min

  • The model works from its training plus the context of this call. The window limits that context, and you pay for its tokens.
  • Between steps, your program keeps the history and sends it again, so input adds up call after call.
  • Keep the context small: clear, trim, summarize or take notes, and watch for lost details.
  • Between sessions, only what you save and load carries over. Live facts come from their official source.
  • Retrieval brings the few relevant passages from a large collection into the context.

Say it in your own words: without looking, explain to a teammate how the assistant "remembers" something (a) from two steps ago and (b) from last week.
